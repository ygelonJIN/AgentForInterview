# 行程子系统与评测

> **什么时候读**：改 `app/trip_gear/` 任何模块、调 `verdict` / `repair` / `spec_match` / `purchase`、改评测场景集或指标、跑消融之前。
>
> 设计意图与分层看 `docs/architecture.md`；本篇只写**动手时容易踩的地方**。

## 改判定之前先认清四种结论不是四种"程度"

`feasible` / `repairable` / `needs_input` / `infeasible` 是四条**不同的出路**，不是严重程度分级。

- **踩过的坑**：把 `needs_input` 当成"比 repairable 更糟"塞进兜底分支，结果所有缺信息的情况都变成"不可行"，用户被直接判死。
- **正确顺序**（`verdict.judge`）：事实型严重问题（温标不够/无货/天数不符）→ `infeasible`，**不能被旁边的信息缺口冲淡**；预算缺口且省不回来 → `needs_input`，把取舍交还用户。判断依据是"这条问题靠改能不能消掉"，不是"ugly 程度"。

## 代价：判定的幅度和排序的幅度不是同一个

`tradeoff.py` 里每个违反有两套幅度：`capped ∈ [0,1]` 用于判定，`raw` 用于排序。

- **为什么**：只用 capped，"超支 2 倍"和"超支 3 倍"同价，修复会以为没进步而提前停住。
- **改法**：新增约束类型时提供 `Delta(capped, raw)`，不要只给一个数。
- **τ 的边界**：τ 只决定 `auto_applicable`（能不能不经确认就动手），**不决定可行与否**。把 τ 接进可行性判断，结论会随一个拍出来的数字漂移，答辩必被追问。
- **权重**：`w = 硬度 × 来源置信度`，务必保持 `w(硬,用户) > w(软,用户) > w(硬,模型推断)`，否则推断出来的"必须"会骑到用户说的"尽量"头上。改权重先跑 `tests/test_trip_gear_tradeoff.py`。

## 修复动作：会改用户明说条件的，一律要确认

`RepairAction.requires_confirm=True` 的动作（目前是 `change_lodging`）不能自动执行，`apply_action` 会直接抛 `PermissionError`。

- **不要绕过**：`verify_node` 把它们放进 `verdict.alternatives`，不进自动修复队列。绕过等于悄悄改需求。
- **换住宿必须算净省**：省下的露营三大件（帐篷/睡袋/防潮垫，按 `qty` 计价）减掉住宿差价，净省 ≤ 0 就不要提。按件数算，别用单价——`qty=2` 的睡袋差一倍。
- **住宿费单列**：`DayPlan.lodging_cost`，不摊进条目。摊进去就算不出"换住宿到底贵了多少"。
- **回退方式**：这几类动作只改内存里的 `gear` / `products` / `itinerary`，跑一遍 `verify` 就回到真实状态，不需要额外的 undo。

## 规格匹配：不知道就是不知道

`spec_match` 三态：`ok` / `insufficient` / `unknown`。

- **unknown 不许当通过**：旧实现只查 `reason` 里有没有"温标"两个字，15℃ 睡袋去 3℃ 的夜里照样通过。任何"有这件东西就算满足"的写法都是回退。
- **规格来源优先级**：已有物品看自身 `specs`，待购看商品 `specs`；两者都有时以自身为准（`resolve_specs`）。
- **商品行里的 `specs` 是 TEXT**：SQLite 取出来是 JSON 字符串，必须先解析，否则等于没有规格。
- **描述兜底只给真有规格语义的品类**：睡袋/帐篷/背包/冲锋衣/防潮垫/登山鞋/跑步鞋。放开会出现"保温杯 500ml → 背包容量 0.5L"这种错数据，而错数据比没数据更危险。
- **抽不到就留空**，交给 `blocking_risk` 决定要不要问。

## 采购可履约：先判有没有货，再判来不来得及

- **顺序不能反**：没货就没有"到货时间"这回事，先报 `out_of_stock`。
- **已出发不算"来得及"**：`days_until` 对负天数返回 `None`，负值会被下游当成"还有时间"。
- **替代款只用硬事实筛**（到货天数 + 库存），价格只排序。便宜但赶不上的款进推荐等于换个说法继续骗人。
- **自提不建模地理位置**：只按"有货"给建议，文案里必须标"假设同城"。

## 商品与预算：不许编、不许沉默

- **无货不是候选**：`shopping._pick` 旧写法 `... if stock > 0] or rows` 会在全无货时把整表退回来，等于推荐无货商品。任何"兜底返回全部"的写法都要警惕。
- **替代要标注**：`ALIASES` 命中意味着品类被换过（保暖层→羽绒），展示必须写明，否则用户以为库里真有。
- **品牌偏好只做软排序**：相当于价格放宽 10% 参与比较；它不能压过预算、规格、可履约。记忆只能影响"选哪个"，不能影响"能不能买"。
- **预算不是上限**：用户报 5000 说的是"打算花这么多"。选完就停，等于把 2594 元余额变成沉默的浪费；要主动升到更好的款。
- **升级要按装备名检索**：拿商品名去搜（"双人防水帐篷"）只会命中它自己，永远找不到更贵的档位。用"帐篷"这种品类词。
- **先排序再花**：按装备顺序一路换会因顺序依赖提前吃掉额度，剩下钱花不出去。先收集候选、再按差价降序落地。
- **差价按数量算**：睡袋 ×2 时"多花 600"是错的，实际 1200。单价差乘数量，账才对得上。
- **不降级保障**：规格未知的候选不许换上去——拿"不知道"换"确定够用"是赌博。

## 记忆候选：不按"能不能写"分级，按"值不值得记"分级

- 写入链路本身是安全的（`save_preference` 只建审批，真写入在 approval graph 之后）。
- 问题在候选生成：模型没输出时走 `_explicit_fact_fallback`，正则把"目的地/天数/预算"造成 `confidence=high` 的候选——**每聊一次行程弹三条确认**。
- 修法：`_durability()` 分 `transient` / `durable`，默认过滤 transient。正则兜底产物必然 transient，等于自动关掉这条路。
- 判据先看稳定线索（喜欢/一般/忌口/常住），再看一次性特征（目的地为/周末/本次）；两边都不像时按 durable 处理，把决定权留给用户。

## 数据迁移：只做加法，先备份，能重跑

商品库加 `specs` / `lead_time_days` 用的是 `scripts/migrate_product_specs.py`。

- **先 `--dry-run`**，看清要改哪几行再执行。
- **改库前自动备份**成 `products.db.backup-specs-<时间戳>`；备份文件已在 `.gitignore`（`data/*.backup-*`）。
- **必须幂等**：列已存在就跳过，已回填的行不覆盖成空。`tests/test_migrate_product_specs.py` 钉住了这条。
- **`init_db.py` 不要用来加列**：它要么拒绝执行、要么 `--force` 整库重建。加字段走迁移脚本。
- 迁移只加列不回填业务数据时，`ProductRepository.search` 的 `SELECT` 也要同步加列，否则查得到表、拿不到值。

## 评测：场景集是"人工出题"，不是"代码出题"

`data/evaluation/trip_gear.spec.jsonl` 一行一个场景，`expect` 手写。

- **绝不能拿被测代码算出 `expect`**，否则是自己给自己出题，准确率恒为 100%。
- **商品内联在场景里**，不查库——否则评测结果随数据库状态漂移，跑两次两个数。
- **时间必须显式传入**：`verify(..., today=...)`、`purchase.days_until(..., today=...)`。用系统日期写测试，明天就红。
- **旧逻辑基线要保留**：`spec_eval.legacy_bag_verdict` 复刻改造前的判定，只活在评测里。删了它就没法回答"改前是多少"。
- **断言评测器本身**：`new_accuracy == 1.0` 之外，还要断言 `legacy_accuracy < 0.6` 且 `legacy_reported_insufficient == 0`，防止打分函数写错后结论"漂亮但没意义"。

## 排错对照

| 症状 | 先查 |
|---|---|
| 结论总是 `needs_input` | `gaps()` 是否把已知项（人数/交通/口径）也算进去了；`NON_BLOCKING_KEYS` 是否漏了新键 |
| 该修复却直接出结果 | `after_verify` 看的是 `verdict.state`；`repair_options` 是否被 `requires_confirm` 全过滤 |
| 修复两轮没收敛 | 动作 `saving` 是否真的落到 `products` / `itinerary` 上；`apply_action` 是否被静默跳过 |
| 温标永远判 `unknown` | 商品 `specs` 是否为 JSON 字符串未解析；迁移是否跑过 |
| 评测跑两次结果不同 | 场景里是否引用了真实数据库或系统日期 |
