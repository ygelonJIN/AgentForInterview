# 关键决策总表

| 决策 | 丢掉/不再采用 | 为什么丢掉 | 改成什么 | 价值 |
|---|---|---|---|---|
| 不做技术全家桶 | 15+ 技术平均用力 | 每项只有 demo 深度，追问两层即露馅 | 每项技术绑定真实问题、边界和降级策略 | 展示工程判断而非技术罗列 |
| RAG 与数据库分工 | 商品也全部走 RAG | 商品是结构化数据，向量检索不够精确 | 商品/订单/画像用 NL2SQL；评价/攻略/FAQ 用 RAG；混合后 Rerank + Top K | 最核心的检索架构问题 |
| 混合语义路由与多 Agent | 靠模糊规则、纯大模型或全部混用 | 意图、执行范式、检索方式混在一起，复合请求只能选一个 Agent | 关键词/上下文/小模型/主模型仲裁分层分类；intent 选 Agent、route 选范式、retrieval 选数据源；shopping+travel 可并行 | 路由可解释且支持明确复合意图 |
| 长期记忆写入策略 | 自动判断"重要性"、原始全量对话直接入库 | LLM 判断不稳定，存储和检索噪声增长 | 提取事实/候选记忆，用户确认；必要时摘要压缩 | 人控记忆边界 |
| 不自动写 Memory | 自动 `save_event`、每轮自动保存 | 每轮都写会制造低价值、重复甚至错误记忆；"买了 37 码鞋"不等于"用户鞋码是 37" | 候选记忆展示，用户逐条确认/拒绝/全部写入；拒绝项不重复出现 | 用户主权、可审计 |
| 记忆提取改成按需按钮 | 每轮回答后自动跑一次提取判断，再把候选推给用户 | 自动判断每轮都要花一次模型调用，且多数轮次没有可写的；用户也说不清"系统刚才判断了什么" | 回答后不判断，对话区只留「提取记忆」按钮；按 `thread_id` 记游标，只送上次之后的用户消息（20 条 / 4000 字封顶），已提取过的不再进模型；提取成功才推进游标，失败可重试 | token 由窗口决定而不是历史长度；"提取了什么"由用户自己触发，可解释 |
| 候选记忆一键写入、再点即撤销 | 走 `interrupt` 审批图，选完再点「确认写入选中」 | 按钮点击本身就是确认，图往返只是多两次跳转；审批图单次 resume，天然不支持"写完再撤" | 每行一个按钮：未写入→写入（MD+向量），已写入→撤销并删除，可反复；全部写入/全部撤销同理；`MemoryApprovalGraph` 退出 UI 路径 | 点一下就生效，撤销是真的删掉，不会留下半截状态 |
| 修复确认放进图里用 `interrupt` 问 | 只在正文写一句"要不要改住民宿"，等用户下一轮自己说 | 下一轮是全新规划，条件会被重新派生，系统并不知道用户在回答哪个方案 | `verify` 把 `requires_confirm` 的动作交 `repair_confirm` 节点 `interrupt()` 问一次，`Command(resume=…)` 带着回答回 `verify`；自动修复仍排在前面 | 确认和执行在同一份状态里，不会各说各话 |
| Token 只记录、不上界面 | 界面上摆「Token 入/出」，或按字符估算 | 供应商根本不回传 usage，两轮跑下来都是「—」；一个恒为空的格子比没有更糟 | 各模型调用的 span 继续记 usage，`done` 事件带 `usage` 字段；界面不展示，等拿到真实回传再说 | 不拿读不到的指标充数 |
| 不自动压缩 | `len(history) % 20 == 0` 自动压缩 | 固定条数与价值无关，会丢失上下文 | `compress_conversation()` 用户手动触发；宁可暂时冗余也不擅自压缩 | 解释可控性优先 |
| MD + 向量库双存 | 只存向量库或只存 MD | 向量库难人工审阅，MD 不利于语义检索 | MD 是权威可编辑记录，向量库是索引；稳定 `memory_id` 同步增删改 | 一致性设计 |
| 敏感副作用审批 | 删除/更新/清空/保存摘要直接执行 | 不可逆、无确认、无恢复 | `start → interrupt → approve/reject → execute` + `idempotency_key` | 安全设计 |
| 删除支付/下单 | `place_order`、`create_payment`、`get_payment_status` | 只是假工具，却会让模型误判项目支持交易 | 只保留只读 `get_order_status`；支付移出范围 | 能力边界诚实 |
| 决策时 Reflection 输出审核 | 输出后持续检查，一旦认为"不完美"就生成全新方案 | LLM 总会认为结果不完美，导致反复重写并形成死循环 | 设置最大迭代次数；提示词改为以既定要求为验收标准，达到要求且无严重错误即结束 | 对 LLM 循环、终止条件和输出稳定性的控制 |
| 按场景拆分 Agent 图 | 一个 orchestrator 里按条件分发、各场景逻辑写在一起 | 场景耦合，改一处影响全部；场景无法单独测试 | shopping / travel / customer_service / general_plan / react 各自成图，外层只做路由 | 场景可独立演进、独立测试 |
| 编排迁到 LangGraph 原生 | 自研编排对象、事件队列、节点计时包装器 | 并发、重试、超时、中断这些能力要自己维护一套 | 删掉 `app/agents/`，改用 `app/graphs/`：`context_schema` + `stream_writer` + `retry_policy` + `tasks` + `interrupt` + checkpointer | 少维护一层框架，行为与官方一致，中断可恢复 |
| 工具按 Actor 绑权限 | 所有 Agent 共用一套工具、越权靠提示词约束 | 模型可以替别的用户取数据 | 工具注册表按 `actor_id` 绑定，越权校验在注册表内完成，模型拿不到不该有的工具 | 权限不依赖模型自觉 |
| 装备协同独立成子图 | 装备靠模型在对话里自由发挥 | 清单无法校验、无法复现 | `trip_gear` 子图：约束派生 → 行程 → 装备 → 已有 → 缺口 → 校验 → 修复，每一步可单独测 | 可校验、可回放 |
| 行程规划统一走 trip_gear | travel 子图也做多天行程规划 | 同一个请求在两处产出，一处有结构化面板、一处只有正文；两套口径迟早会漂 | `nodes._is_trip_plan` 把纯旅行的 `plan_trip + plan_and_execute` 改派 `trip_gear`；`shopping + travel` 复合请求仍走 composite | 规划格式一致，结构化结果只在一处产生 |
| 缺人数/出发日期先追问 | 缺了就用默认值（按 1 人、按今天）先算出一份完整方案 | 默认值会一路算进预算、天气和装备数量，用户看到的是一份"按 1 人"的方案却不知道被假设了什么；问一句、点一下就能补 | `_blocking_gaps` 把目的地、天数、人数、出发日期一起当阻塞项，追问卡片给可点选项；补答后 `ensure_people` / `ensure_start_date` 重写清单；没日期时仍整组不判时效 | 方案里每个数字都对应一个用户确认过的条件 |
| 四态结论 | 有预算问题就进修复循环 | 修不动的问题（温标不够、无货）在修复里空转 | `feasible` / `repairable` / `needs_input` / `infeasible`；修不动的直接给替代方案与放弃清单 | 修复有明确出口 |
| 规格匹配三态 | 规格未知默认放行 | 等于替用户假设"应该够用" | `ok` / `insufficient` / `unknown`；unknown 标风险并追问 | 不虚报"满足" |
| 预算当计划而不是上限 | 花不完就剩着 | 预算说 5000 是"打算花这么多"，不是"最多花 5000" | 同品类换更好款直到用得差不多；四条边界：只用库内商品、不超预算、不降级保障、不动用户明说条件 | 预算利用率可解释 |
| 打分选品 | 按价格取第一件 | 卡线的便宜货会胜出（5℃ 睡袋应付 10℃ 露营） | 0.45×参数匹配 + 0.25×参数质量 + 0.20×口碑 − 0.15×预算占用；参数表按品类分开 | 同价位选到更合适的款 |
| 统一 NLU 层 | 分类器、共享约束、行程事实各写一套正则与词表 | 同一句话在两条链路抽出两个人数、两个目的地 | `app/nlu`：`numerals`（中文数字按位值还原）+ `lexicon`（唯一词表）+ `slots`（唯一槽位）+ `signals`（加权打分） | 改一处全网生效，42 条人工期望场景集兜底 |
| `people=None` 表示"用户没说" | 默认 1 人，并当成用户说的 | 界面显示"1 人"是编的 | `None` + `effective_people`（计算仍按 1）；缺了就进追问卡片，用户不答才退回展示"未指定（按 1 人计）" | 默认值不冒充用户输入 |
| 装备清单只由商品库决定 | 规则造 20 个内部装备名 → 搜不到也列 → 显示"未匹配/自备"；靠别名表把装备名翻成商品名 | 清单里出现买不到的东西；别名表随商品增长维护不动，且只覆盖被枚举到的词 | 需求直接用真实商品词表达，检索不到就从清单移除（不占行、不报数）；删掉 `BASE_ITEMS`（14 项自备）、`ALIASES`、`_OWNED_ALIASES`；已有物品只做词形包含匹配 | 清单每条都能下单；新增 SKU 不改代码 |
| 目录摘要给模型看 | 让模型凭空想象"露营要什么"；或按评分取前三件当示例 | 模型有常识但不知道我们卖什么；按评分取样会把帐篷/睡袋挡在模型视野外 | `catalog.py` 把品类 + 品类词（从商品名抽，如"暖冬 -25℃羽绒睡袋"→"羽绒睡袋"）塞进规划提示词 | 模型的选择落在真实品类上，摘要长度只随品类数增长 |
| 商品检索换 2-gram 索引 | `LIKE '%词%'` 全表扫描 | 前导通配符走不了索引，是规模上的第一道墙 | FTS5 + 自建 2-gram（trigram 查不到两字词、unicode61 不切中文、jieba 要加依赖）；两字词精确、三字以上 LIKE 复核、单字退 LIKE | 20 万行 32ms → 8ms，结果与 LIKE 一致 |
| 模型挑款：批处理 + 缓存 + 兜底 | 每件装备问一次模型 | 十项装备就是十次调用，成本与延迟都不可接受 | 一次调用挑完；候选由打分裁到每项 4 个；候选少于 2 个不问；结果缓存一小时；任何异常回落打分 | 每次出行 1 次调用、约 1k token，且不随库存增长 |
| 活动证据走真实 provider | 本地 `data/activities/*.txt` 兜底所有城市 | 兜底不判断覆盖范围：问"新加坡"时拿到了千岛湖露营、黄山、泰山，等于把别的城市资料冒充本地证据 | `get_local_activities` 先走 provider 链（Ticketmaster → Photon/OSM → 该城市本地文件），拿不到返回 `available: False` + 原因，记成 `ok: False` 的工具调用走降级 | 全球任意城市都能答真实场所；答不出时明确说答不出 |
| 地名宁可拒答不猜 | 查不到就取最接近候选 | 中文地名在 GeoNames 里常命中国内同名地点（`东京` → 浙江一个村，`纽约` 直接查不到），错坐标会让天气、路线、活动三处一起歪 | `tools/geo.py`：别名表带国家码校验 + 按行政级别与人口择优 + 表外标 `uncertain`；Nominatim 死分支删除 | 错数据的代价高于"没数据"，且错在源头会污染整条链 |
| 目的地推荐是示例目录而非全球库 | 假装能推荐全世界 | 没有免 key 的全球目的地库；8 个国内城市撑不起"随机问世界城市" | 目录补到 30+ 城市（必须都能被 `geo` 解析），返回值带 `note` 说明是示例与估算；目录外直接让用户说目的地；排序改为"命中标签数优先"再比价 | 推荐不越界，且不会推荐一个查不到天气的城市 |
| 审核快路径按行程天数判 | 用 `len(evidence_steps) == 1` 当"任务简单"的判据 | 加上活动证据后一天行程也有两条，"只有一条"这个判据把快路径彻底堵死；而放宽成"证据干净就跳过"会让两天以上行程也跳过模型审核 | `days == 1` 且每条证据 `completed`、无 `warning`、无 `stale` 才走确定性审核 | 快路径恢复，同时保住"多天必须模型审核"这条边界 |
| 场次由用户提供，不做活动 API | 接 Ticketmaster / 抓大麦秀动来查"某天演什么" | Ticketmaster 要 Key 且无中国业务（`.cn` 域名不存在），秀动接口要服务端签名，大麦是 JS 反爬，场馆官网是前端渲染——没有一个能长期稳定跑在中国城市上 | 活动证据只给**场所**（分"可买票参加"与"只是可去"两组）；用户已订的活动走 `TripFacts.fixed_events`，系统负责钉进日程、算进预算、检查与返程和相邻安排的时间冲突 | 不依赖任何不稳定接口，且"把演出排进行程"这件事本来就是系统该干的活 |
| 多城市按顺序均分到天 | 一个目的地字段装多城，或让模型自己分 | 模型分法每次不同，天气、渲染、校验没有确定依据；一个目的地字段又表达不了"第几天在哪" | `DayPlan.city` + `assign_cities`（顺序均分、余数给前面）；天气按城市×天取，模型没写 city 就按分法补 | 多城行程可复现、可校验，天气不再拿一个城市代表整趟 |
| 只加"事实型"外部工具 | 把推荐器、票务、比价也接进来 | 推荐器无法验证、票务接口不稳定（12306 反爬、大麦签名、航班要 key），接进来只会把"编数据"换个位置 | 外部工具只收"查回来能进约束/校验"的事实：天气、空气质量、汇率、法定假日、路线、营业时间；票务与场次一律由用户提供 | 每个工具都能在清单里被追溯，失败的代价是"少一条证据"而不是"多一条假数据" |
| 天气按整趟逐日查 | 只查出发那天、拿一个温度代表整趟 | 第 2 天降温、第 3 天下雨全被抹平，清单里还看不出这几天没查过；按天各发一次请求又浪费配额 | `get_weather_forecast(city, start_date, days)` 一次请求返回逐日数组；清单逐日一条；装备按整趟最冷/最湿那天派生；拿不到就写不可验证 | 天气证据覆盖全程且可见，装备不再赌第一天 |
| 出发地与目的地拆成两个槽位 | 一个 `destination` 槽位二选一 | "我在广东，我要去上海"里两个地名都在，谁先命中谁胜出，整趟行程的方向会反 | `slots.parse_origin` 单独抽"我在 X / 从 X 出发 / 上海出发"（裸写法只认地名表里的词，否则"后天出发"会被当成出发地）；`parse_destination` 把强动词（去/到/回/飞）排在"在"前面 | 起点不再被当成终点，也不会以"行程城市"的身份混进 itinerary |
| 约见新增 `appointment` 一档 | 沿用 `booked` / `planned` 两档装"有一天去找朋友" | 装成 `booked` 是假装用户买过票（还会挤掉别的安排），装成 `planned` 又会被行程挤掉；两档都表达不了"这趟要留出半天、哪天可以调" | `FixedEvent.status` 第三档：地点与事由固定，日期由排程决定（没说哪天就排中间那天），占半天并清掉同时段的安排，不删返程 | "有一天要见的人"一定排得进去，但不假装是已订行程 |
| 入口语料回归集 | 只按单条说法修解析、靠人肉复测 | 改一处崩一处，永远在被"再说一句又错"追着修 | `data/evaluation/nlu_corpus.jsonl` 人工标注 52 句 + `tests/test_nlu_corpus.py`；遇到新说法先加语料再改逻辑 | 解析改动有回归闸门，不再逐条报修 |
| 省份不是城市 | 拿省名直接当目的地查天气、路线 | "广东"会被地理编码落到四川同名地点，天气路线全歪；一律反问又会让"去很多城市"的人卡在追问里 | `lexicon.PROVINCES` + `PROVINCE_CITIES`；只说省份就反问具体城市；答"很多城市/你定"则**保留用户点名的城市**、缺的用常用城市补齐（7 天 3 城封顶）并标"规则推导" | 既不出错数据，也不把授权当缺信息，更不拿默认城市顶掉用户点名的那个 |
| 追问带选项、补答重写清单 | 只回一段"请补充：目的地、天数" | 用户还得自己组织一句话，解析可能再错一次；多件事要来回问好几轮 | `interrupt` 带 `questions`（每题 A/B/C 可点 + 自定义），前端渲染成卡片；补答后 `ensure_destination` / `ensure_people` 重写清单旧值 | 一次问清多件事，点选即解析，清单与事实不再打架 |
| 每轮事件随消息入库 | 只存正文，结构化面板只在当轮可见 | 切回历史会话只剩文字，01–05 面板与过程日志丢失 | `ConversationStore.annotate_last_assistant` 把 `process_events` 合并进该轮助手消息，历史回看据此重放 | 会话可回放，演示不依赖"当时在现场" |
| 本地攻略按主题选择 | 全文关键词扫所有攻略文件 | 文件一多，任何一句都能命中"杭州/露营"之类的词，拼出来的参考又长又不相关 | `_GUIDE_TOPICS` 主题到触发词表，命中哪个主题读哪篇；都对不上才退回前 3 篇泛化参考 | 参考与请求同题，token 也可控 |
| 已有物品不靠关键词猜 | 正则抓"有 X"就当已有，再把没匹配上的补进清单 | "要有汕头"里的"有"是打算不是现状，结果凭空多一件"已有装备"；再加一张装备词白名单只会跟着商品库一起烂 | 负向环视排掉要/想/需；名字落在地名表里的直接丢弃；匹配不上的仍补进清单（兜住"我有件西装外套"） | 已有清单不会出现地名，也不用维护第二张词表 |
| 行程城市只认事实分配 | 模型写 day.city 就采信 | 模型会把出发地排成第一站，面板标题写广东、前半程在上海 | `_from_plan_output` 用 `assign_cities` 的结果覆盖模型写的城市 | 城市与天数分法可复现，标题和内容对得上 |
